# wry 0.55.1 本地补丁（轻匣）

本目录是 crates.io 上 `wry 0.55.1` 的完整副本，由 `src-tauri/Cargo.toml` 的 `[patch.crates-io]` 引入，只改了一处。

## 改了哪里

`src/wkwebview/class/wry_web_view_delegate.rs` 中 `WKScriptMessageHandler` 的 `did_receive`（`userContentController:didReceiveScriptMessage:`）：在读取消息体之前判断 `msg.frameInfo().isMainFrame()`，非主 frame 发来的消息直接丢弃，不再交给 `ipc_handler`。

其余文件与发布包逐字节一致（仅删除了注册表解压标记 `.cargo-ok`）。

## 为什么改

插件架构 0.2 把插件放进主 WebView 内的沙箱 iframe（方案第 10.2 节）。PL11 实测发现：

- wry 注册的 `window.webkit.messageHandlers.ipc` 对 iframe 可见；
- Tauri 把 iframe 发来的请求当作 `main` 视图的本地请求处理，唯一的屏障是主页面闭包里的调用密钥。

沙箱 iframe 读不到调用密钥，现状不可利用；但一旦密钥泄露，插件就能调用 `main` 权限内的全部命令。轻匣只有主页面需要这条通道，插件一律经 `MessageChannel` 端口由宿主页面转发，因此在 wry 层丢弃非主 frame 的消息，把“密钥是唯一屏障”变为纵深防御。

## 升级 wry 时如何核对

1. 用新版本的发布包替换本目录，保留本说明文件，并同步修改 `src-tauri/Cargo.toml` 中 tauri 所需的 wry 版本。
2. 在新版本中找到 macOS 脚本消息处理器（搜索 `didReceiveScriptMessage` 或 `IPC_MESSAGE_HANDLER_NAME`），在调用 `ipc_handler` 之前重新加入同样的判断。若上游已自带“只接受主 frame”或等效开关，改用上游做法并删除本补丁。
3. 确认补丁生效：在 `src-tauri` 下运行 `cargo tree -i wry`，输出中 wry 应带本目录路径，例如 `wry v0.55.1 (…/src-tauri/patches/wry)`。版本号与 tauri-runtime-wry 要求不一致时，cargo 会给出“patch was not used”警告，此时补丁没有生效。
4. 运行时复测：用 PL11 逃逸探针（分支 `pl11` 的 `tests/fixtures/iframe-probe/run-probe.sh`，不带 `--keys`）跑“模拟密钥泄露”用例，日志 `/tmp/qingbox-iframe-probe.log` 中不应出现 `from` 为 `iframe:webkit:泄露密钥` 的 `ping` 记录，也不应出现由 iframe 触发的 `plugin_call`。
